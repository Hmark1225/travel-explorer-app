# Deploying the separate admin app

Use a separate Vercel project with repository root directory `admin`, framework Next.js, `npm ci` install and `npm run build` build command. The root Expo app/package/lockfile remain separate. The admin package pins its Supabase SDK and framework dependencies and has its own lockfile. Use Node 24 or a currently supported Node version meeting Next and SDK engine requirements.

Configure only the actual HTTPS Supabase URL, publishable key and actual HTTPS admin origin from `.env.example`. NEXT_PUBLIC values are browser-visible. Do not put secret/service-role keys, database passwords, S3 secrets or partner API credentials there. Set these separately for preview and production; preview should use a staging Supabase project. Do not point unaudited preview code at production. No live deployment URL is invented or claimed here.

Apply the reviewed migration through a controlled database deployment, after reconciling the existing foundation migration ledger described in README. Vercel build does not execute migrations or grant admin roles. Verify first-admin membership manually. Confirm Auth email/password policy, verified emails, rate limits, disabled unwanted signup and appropriate session expiry. MFA and finer approval roles are recommended follow-up requirements for higher-risk multi-editor operations, not implemented guarantees in v1.

Before enabling use: check public views, advisor exceptions, storage bucket privacy/policies and actual unauthenticated denial; test an ordinary verified Auth user versus a manually granted admin; test version conflicts, complete bilingual publication, private uploaded photo review and public image delivery; verify the existing mobile app and local collections. Confirm the new public image route works under the actual origin, and that archiving stops new delivery while old signed links expire within five minutes.

Rollback by disabling the separate admin deployment or removing an administrator's membership. This does not modify mobile guest collections. Do not drop content, audit, Auth or Storage tables to roll back a UI deployment. Keep the migration as history and use reviewed forward fixes. Retain backups and review source/audit retention obligations. Use the foundation's non-destructive public-read emergency stop only if that separate public API needs suspension.
