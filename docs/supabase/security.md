# Security boundaries and administrative foundation

Every exposed base table has RLS enabled and explicit anon/authenticated grants. Anon has **no base-table permissions**. Authenticated users have table CRUD grants subject to RLS: content/source/photo/partner tables allow only a private administrator membership check; profiles/collections/trips permit only the owner. Administrators do not receive a blanket exception for other users' private data. The private admin membership table has RLS, no client grants and no self-assignment policy. `is_admin()` is SECURITY DEFINER with an empty search_path and uses only auth.uid(), not editable claims/profile fields. Schema CREATE permissions and default public grants are restricted. Service-role grants are explicitly server-only and inherently bypass RLS; protect that credential and database-owner access separately.

The public API consists of `travel_destinations`, `travel_attractions` and `travel_photos`. These are deliberately owner-executed, security-barrier views rather than security-invoker views: ordinary roles cannot SELECT raw content, even for published records. The views explicitly filter published + approved + reviewed content and parent publication, require en/hu translation completeness, gate photo rights/assignments, and build allowlisted JSON objects. No SELECT *, raw editorial record, editorial_notes, private reviewer name, partner tracking configuration or private account data is projected. Tests query the views as anon and authenticated roles and verify both allowed and denied paths. Adding fields requires a projection and privacy review, not expanding raw grants. Do not accidentally turn public views into unfiltered owner-executed queries.

A future dashboard should use authenticated JWTs and administrator RLS, never a service-role key in browser code. Required CRUD features: role-gated access; draft creation; explicit parent/child selection; stable non-renamable IDs; English/Hungarian completeness; source/evidence editing; separate editorial review, approval and publish actions; archive instead of deleting referenced content; coordinate and official-URL verification; full rights/subject review; safe public provenance separation; assignment approval; audit history; optimistic concurrency using updated_at; validation/error reporting; pagination; least-privilege operator accounts and role revocation. The current membership grants all editorial CRUD to authorized administrators; finer reviewer/publisher separation and immutable audit history need another migration before a multi-person dashboard launch. There is no public content editor on this branch.

Foreign keys bind attractions to destinations, sources through junctions, and photos to assignments. Private saved/trip targets must be publicly available on insertion/update. Trip item ownership is enforced both by auth.uid() and a composite (trip_id,user_id) FK. Owners may read/remove their old items after content is archived. Users cannot reassign ownership to another UUID, edit another profile, or join their item to someone else's trip. Anonymous users cannot access private rows at all. Revoking a content administrator role does not depend on JWT refresh because membership is checked in the database.

The local tests use actual PostgreSQL via PGlite, with a **test-only** minimal auth.users/auth.uid()/role bootstrap. Never deploy `supabase/tests/bootstrap.sql` to Supabase; hosted Auth already supplies those components. The tests do not validate hosted Auth token issuance, API gateway configuration, connection pooling, backups or project-specific grants that existed before these migrations. Repeat tests against a disposable Supabase staging project before production. No compliance or production security guarantee is made.
